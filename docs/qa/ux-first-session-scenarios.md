# UX-аудит первой сессии — каталог сценариев (v0.7.0)

> Единый рабочий файл фазы 1: все сценарии первой сессии + все вопросы для инвестигейта.
> Фаза 2 (цикл глубокой проверки) пишет результаты в `docs/qa/ux-investigation-report.md`
> и отмечает статус в чек-листе там же. Делаем, пока не останется непроверенных сценариев.

**Источники:** аудит всей документации (README, CHANGELOG, architecture, frontend-conventions,
runbook-daemon/orchd, traceability, backlog, platform-overview, спеки S2/S3/S4/S-EXT/S-IDEA) +
покомпонентная инвентаризация `src/components/**` + повербная инвентаризация
`orchd socket_server` (77 verbs) / `sessiond` (14 verbs) / `commands.rs` / `broker.rs`.

## 0. Словарь (маппинг терминов владельца → сущности приложения)

| Термин владельца | Сущность в приложении | Где живёт |
|---|---|---|
| Проект | `Project` (status: active / archived) | Sidebar «+ проект», ProjectPanel |
| Гипотеза | `Idea` (⌘K-капчур; lifecycle: captured → researching → specced → in_dev → shipped → archived) и её проверенная форма `Insight` (fit_verdict: fit / no_fit / unknown; status: new / accepted / archived) | Таб «Идеи», «Инсайты», research-конвейер |
| Фича | `DomainTask` (status: backlog / todo / waiting / progress / testing / done; source: idea / insight / bug / plan) | Таб «Задачи» |

⚠ **Открытый вопрос O-1:** подтвердить маппинг. Если «гипотеза» = только Idea (без Insight) или
«фича» = что-то ещё — сценарии эпиков E/G/H пересобрать.

## 2. Каталог сценариев

Колонки: **Старт** — откуда начинается; **Шаги**; **Ожидаемо** — результат + что должен
увидеть пользователь; **Ошибки/edge** — как должна выглядеть обработка; **Проверить** —
вопросы инвестигейта (сверх стандартного набора) + Refs на подозрения.

**Стандартный набор проверок для КАЖДОГО сценария** (не повторяется в таблицах):
1) обработка есть и честная (не проглочено, не наврано); 2) логи на success/fail-путях
(и что именно логируется — без секретов); 3) push/refresh доводит экран до консистентности;
4) `orchdDown`-гейт где применимо; 5) баг есть/нет.
